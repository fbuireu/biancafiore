# src/application

The anti-corruption layer between the CMS and the domain. `dto/` maps and `entities/` loads. See ADR 0012 for the layering, and ADR 0021 for why the content is in EmDash, integrated into the site: this folder is what made moving it there from Contentful (ADR 0002) a change of mappers rather than of pages.

## dto/ (EmDash → domain)

```
dto/<concept>/
  <concept>DTO.ts   # export function createX(raw…): XDTO[]
  types.ts          # XFields (the collection's fields, by their EmDash slugs) + RawX = CmsEntry<XFields, Reference>
  utils/            # mapping helpers owned by this concept
  index.ts          # re-exports the DTO only
```

A DTO fed by more than one query takes them as one object, not as separate arguments: `createAuthors` maps `{ rawAuthors, rawArticles }`, `createArticles` maps `{ rawArticles, rawAuthors }` and `createTagIndex` maps `{ rawArticles, rawAuthors }`, which is exactly what `fetchArticlesAndAuthors` hands back: the Articles, and `creditedAuthors` of them. A raw type names the reference fields its mapper reads, `RawArticle<"related_articles">` the hand-picked Related Articles, so a loader that asked for fewer cannot hand it to a mapper that needs more; `AnyRawArticle` is either, for the mappers that read no reference. `RawAuthor` is not an entry at all but a `CmsByline`, the credit EmDash hydrates onto every Article.

**The content model this folder maps** is [`seed/seed.json`](../../seed/seed.json), applied once to an empty database:

| Collection | Fields | Identified by |
| --- | --- | --- |
| `articles` | `title`, `content` (Portable Text), `description`, `publish_date`, `featured_image`, `featured_article`, `is_favorite`, `is_republished`, `original_source`; the `tag` taxonomy; references `related_articles`; credited to bylines | its slug, which addresses the page |
| `cities` | `name`, `latitude`, `longitude`, `start_date`, `end_date`, `description`, `image` | its name |
| `projects` | `name`, `description` (Portable Text), `image` | its slug, else its slugified name |
| `testimonials` | `author`, `quote`, `role`, `image` | the Quotee's name, which the CMS field still calls `author` |

Tags are not a collection: they are the terms of EmDash's `tag` taxonomy, which a collection query hydrates onto every Article as `terms.tag`, and `tagsOf` in [`dto/article/utils/tags.ts`](./dto/article/utils/tags.ts) is the one reading of them. Authors are not a collection either: they are EmDash's bylines, credited on each Article in order and hydrated onto it by the same query, so the Articles alone answer who wrote what. A byline carries a display name, a slug, a bio and an avatar; the three things an Author has beyond those are byline custom fields, `job_title`, `current_company` and `social_networks`, keyed in `AUTHOR_FIELD` ([`dto/author/types.ts`](./dto/author/types.ts)). Custom fields are not in the seed: they are registered through EmDash's `/_emdash/api/admin/byline-fields`, which the import does. A byline field is a `string`, `text`, `url`, `boolean` or `select`, never a repeater, so `social_networks` is a `text` field holding one network per line as `Name | URL`, and `socialNetworkUrls` beside `createAuthor` reads the URL off each line and keeps it only when it is `http` or `https`.

- **DTOs are pure on purpose.** They take already-fetched raw entries and return domain DTOs: no `fetchEntries`, no Effect, no env, no `await` on I/O. Every `create` is synchronous, and deterministic: a date leaves as a UTC instant (`publishDateISO`) or a UTC year (`createPeriod`), so the time zone the Worker renders in never moves it. Nor does a mapper order anything itself: the Blog's order is `sortFavoriteFirst` and the Latest Article is the head of `sortReverseChronological`, both domain rules. The line is I/O, not layering: `@infrastructure/images/imageOptimization` *is* imported here (`getOptimizedImageUrl` and `getOptimizedSrcset` only build a CDN URL string), so is `@infrastructure/images/imagePlaceholder` (`imagePlaceholder` decodes a blurhash in memory), `@infrastructure/cms/media` for `mediaFileUrl`, which turns a bare media key from an Article's SEO panel into a path on EmDash's media route, and so is `@infrastructure/cms/entries` for the `CmsEntry`, `CmsByline`, `CmsMedia`, `CmsReference` and `CmsTerm` types it answers with.
- **EmDash types stop here.** `CmsEntry`, `CmsByline`, `CmsReference`, `CmsTerm` and everything `emdash` exports may appear in this folder and nowhere downstream. The domain never sees a `data`, a `references`, a `terms` or a `bylines`. Portable Text is the exception [ADR 0023](../../docs/adr/0023-portable-text-renders-in-the-ui-through-emdash.md) makes on purpose: it is an open format rather than EmDash's, the domain carries it as `portableTextSchema` (an array of typed objects it never looks inside), and the page hands it to `emdash/ui`'s renderer, so what crosses the boundary is the blocks, prepared here, never a CMS type.
- **The CMS's raw values are translated here.** `flagOf` in [`dto/shared/flags.ts`](./dto/shared/flags.ts) is the one reading of an editorial flag, and every flag goes through it: it takes a boolean and the `0` or `1` SQLite stores alike, so a flag reads the same whichever of EmDash's surfaces it came through. A field the editor never filled in is absent rather than `null`.
- **Where each mapping lives.** A `utils/` helper lives under the DTO it serves, and one that several DTOs share lives under the concept it maps. `createAuthor` in [`dto/author/utils/author.ts`](./dto/author/utils/author.ts) turns a byline into the fields a Byline and the authors collection carry, refusing one with no avatar by its slug and id: `createAuthors` spreads it and adds the Latest Article, and `createArticles` calls it for the Byline it embeds. The Author Tag takes the part they share from `authorIdentity` beside it, the trimmed name and slug, and `credits` answers whether an Article's bylines name an Author, which the Latest Article and the Author Tag match on, while `creditedAuthors` collects every byline credited on any Article once. `tagIdentity` in [`dto/tag/utils/tag.ts`](./dto/tag/utils/tag.ts) does the same for a Tag, and `articleTagSlugs` beside `tagsOf` for the Tags an Article carries, so Related Articles and the Tag Index match on one trimmed string. Both identities refuse a name or a slug that is only padding, naming the entry by its id, since the Tag Index files an entry under the first letter of its name and a page needs a slug.
- **An Article no byline credits is refused here**: `bylineAuthor` beside `createAuthor` takes the Article's first credited byline, the one its Byline names, and throws naming the Article when there is none, so the page fails rather than rendering an Article with no byline. **An image is refused the same way**: `createImage` in [`dto/shared/images.ts`](./dto/shared/images.ts) checks it against a zod schema with `.validate()` (a resolved `src`, numeric dimensions and a mime type) and throws naming the media's id otherwise, so the failure names the asset rather than whatever tried to read it.
- **One raw entry, one address.** `articleSlug` in [`dto/article/utils/reference.ts`](./dto/article/utils/reference.ts) is the only place a raw Article entry, or a reference to one, becomes the string that identifies it, and `articleReference` beside it is the only place one becomes a `Reference<"articles">`, so no `{ collection: "articles" }` literal is written anywhere else in this folder, and `createArticles` takes its own `slug` from the same call. `articlePublishDateISO` beside them reads the publish date through the domain's `publishDateISO` and rethrows a refusal that names the entry by its slug and id, the domain's own as its `cause`, so a request that stops on a bad date says which entry to open (`createCities` does the same for a City's Period, naming the City), and `articleIsFavorite` reads the Favorite flag. That is what makes the id the articles collection is keyed on and every reference aimed at it equal by construction: the Tag Index, the Author's Articles and an Article's Related Articles all derive from one normalisation, and the consumer, `resolveArticle`/`resolveArticles` in `@modules/core/utils/entries`, drops a reference it cannot find without a word.
- **Every Slug is trimmed here**, and so are the Author and Tag names the Tag Index sorts and the keys of the other collections: a City's name, a Project's `id` and a Quotee's name. A comparison downstream that has to `.trim()` before it matches is a sign a mapping was skipped.
- **One concept, one decision.** `createRelatedArticles` in [`dto/article/utils/articles.ts`](./dto/article/utils/articles.ts) is the only module that answers what an Article's Related Articles are. It owns the branch [GLOSSARY.md](../../GLOSSARY.md) defines (hand-picked, else inferred from shared Tags), so `createArticle` hands it the whole batch and takes the answer. A hand-picked list is one the editor filled in at all, and it is read only for the Article a page shows, the one place it is rendered: everywhere else an Article carries the inferred list, which is cheap because the Tags are already on every entry. Each pick is resolved through `publishedEntriesOf` in [`dto/shared/references.ts`](./dto/shared/references.ts) to the published Article it names, by database id, so a pick that is not published is dropped and the inference does not step in for it. It leaves the Article out of its own list in both branches, by `articleSlug`. The cap, `INFERRED_RELATED_ARTICLES_LIMIT` (6), applies to the inferred branch only: an Author who picks eight means eight.
- **The site settings, the menus and an Article's SEO panel are mapped here too, and every URL an editor typed is checked before it can reach an `href` or a `<meta>`.** `createSiteSettings` in [`dto/site/siteDTO.ts`](./dto/site/siteDTO.ts) reads EmDash's site settings: the title and tagline become the site's name and description, each network under *Social* is kept only when its value is an `http(s)` URL, and the SEO section gives the title separator, the default share image and the Google and Bing verification tokens. `createMenu` in [`dto/menu/menuDTO.ts`](./dto/menu/menuDTO.ts) reads a menu's items: a label may bracket the part that links (`back to start [Home]`), and the words around it render as prose, which is how the header keeps its phrasing in an editable menu. `articleSeo` in [`dto/article/utils/seo.ts`](./dto/article/utils/seo.ts) reads the SEO panel EmDash keeps on an Article (`supports: ["seo"]` in the seed) and is absent when the editor set nothing, so the page keeps deriving its own. Both hand back final values: a value the editor left empty, or one that fails its check, is replaced by today's (`SITE_DEFAULTS` in [`@const/site.ts`](../const/site.ts), `DEFAULT_MENU_ITEMS` in [`dto/menu/defaults.ts`](./dto/menu/defaults.ts)), a menu that does not exist answers today's links and one emptied by the editor stays empty, so `readSiteSettings` and `readMenu` in `@modules/core/utils/entries` only read and a component only maps. A prerendered page (the legal pages) passes `prerendered: true` in its entry filter, and `contentLoader` then answers from the loader's `loadPrerendered`, which is the DTO's defaults, without reading EmDash: a build has no database worth reading, and one that answered would bake its values into a static page. The rules live in [`dto/shared/urls.ts`](./dto/shared/urls.ts): a menu item is dropped unless its URL is a path on this site (`/…`, never `//…`), a fragment, or `http:`, `https:`, `mailto:` or `tel:`; a share image is kept only when it is a path on this origin or an `http(s)` URL.
- **Derivations delegate to `@domain/<concept>/rules`.** The DTO decides *which* raw field feeds a rule; the rule decides *what the value means*. Don't inline reading-time maths or description trimming here.
- **An asset URL arrives relative, on this Worker's origin.** EmDash stores a storage key, and `resolveMedia` in the CMS client turns every one into a path on EmDash's media route before a mapper sees it. `imageSchema.url` is therefore a path, and whatever needs an absolute URL (the Open Graph image, the JSON-LD `image`) gets it from `absoluteUrl` in `@const/routes.ts`, the tree's one reader of the site origin, at the point it is written out. `createImage` also decodes the stored `blurhash` into the `placeholder` a `BlurImage` shows while the image loads, and builds the `shareCrops` the JSON-LD lists as transform URLs on the same origin.
- **Portable Text leaves here ready to render.** [`dto/article/utils/content.ts`](./dto/article/utils/content.ts) emits no HTML, and the page decides nothing: `prepareArticleContent` hands it blocks whose every field a component only has to write out, and `ArticleContent` renders them with `emdash/ui`'s `<PortableText>` (ADR 0023). A heading becomes an `articleHeading` block carrying its tag, its unique anchor and, from h2 down, the `--section-N` scope the Table of Contents animates on. An image block becomes its CDN `src` and `srcset`, the placeholder decoded from its `blurhash` (an older block keeps it in its asset's `meta`), its alt falling back to the Article's title, and the `layout` its alignment names, looked up only for an alignment `IMAGE_LAYOUT` knows, so a key every object inherits (`toString`) names none. A split block becomes its image's `src` and `srcset`, its alt and its text. An iframe holding a YouTube or Vimeo watch link becomes that player, and a `videoEmbed` an earlier import wrote becomes the same `iframe`, through `playerEmbed` in [`dto/shared/embeds.ts`](./dto/shared/embeds.ts), which the import calls too. A block whose fields fail its zod schema (`.validate()`) is dropped, an iframe served over anything but `https` among them, and so is a type no component renders (`EMDASH_RENDERED_TYPES` lists the ones EmDash's own components take), because `<PortableText>`'s fallback for an unknown type is a hidden warning in the markup. A Project's description goes through `prepareProse` in [`dto/shared/portableText.ts`](./dto/shared/portableText.ts): its links settled and its text blocks kept, nothing else.
- **An internal link is a route, not a string, and every link leaves here settled.** `prepareLinks` in [`dto/shared/portableText.ts`](./dto/shared/portableText.ts) marks a link to another site `blank`, which EmDash's link component turns into `target="_blank"` and the article stylesheet into the ↗ cue; turns one to the production domain into its path, so a preview stays on its own origin; opens a tag page (`isTagPath` from [`@const/routes.ts`](../const/routes.ts)) in a new tab with no cue; keeps `mailto:` and `tel:` as written; and drops a link it cannot make a URL of, or one of any other scheme, keeping its label. It does the same inside a table's cells, against the table's own definitions. The canonical-domain test (the base URL an authored link is resolved against to decide whether it is external) is deliberately *not* the site origin `absoluteUrl` uses: it asks whether the editor typed a link to the production domain, which is the same question in every environment, preview included.
- **Every heading's anchor is unique in its Article and never empty.** `createAnchors` in [`dto/article/utils/content.ts`](./dto/article/utils/content.ts) derives it once from the heading's text through `slugify`: a repeat takes `-2`, `-3` and so on, the h1 counting among the headings, and a heading `slugify` strips whole (only punctuation, or a script outside Latin) takes `section`, numbered the same way, so the Table of Contents entry and the body spell one id. Such a heading reads `section` and not a transliteration, which stays a question for multi-language.
- **A video is EmDash's `iframe` block, not a block of ours.** EmDash's editor turns a YouTube or Vimeo link pasted into an iframe block into its player, and `playerEmbed` writes the same shape for the import and for a block that still holds a watch link; EmDash's `Iframe` renders it sandboxed inside `.emdash-iframe`, sized by the width and height the block carries. A generic iframe carries none, and `_article.css` sizes that one from its wrapper instead (see the modules guide).
- **Optional CMS fields get their defaults at this boundary**, so the domain DTO is total: `flagOf(…)` for the editorial flags an author may simply not have ticked, `|| prose` for a description the editor never wrote or cleared (EmDash keeps a cleared field as `""`, which `??` would pass through), `prose` being the text of the Article's text blocks alone, so no caption, cell or code reaches the meta, Open Graph and feed descriptions, and and nothing for a Project with no description, whose `prepareProse` answers no blocks. Every default written here is asserted against the DTO layer, so removing one from the code fails the docs test.

## entities/ (Astro live collections)

```
entities/<plural>/
  <plural>.ts   # export const <plural> = { loader: contentLoader({ name, load, identify }), schema }
  index.ts
```

Each module exports a plain `{ loader, schema }`, and [`src/live.config.ts`](../live.config.ts) wraps every one in `defineLiveCollection` beside EmDash's own `_emdash`: Astro refuses a live collection defined anywhere else. A loader runs on the request that reads it, so it is the only place content I/O happens per request. They share `contentLoader` in `entities/collection.ts`, which turns a `load` that answers mapped DTOs into Astro's `loadCollection` and `loadEntry`, keys each entry with `identify`, and hands a failure back as `{ error }`, so a page decides how to answer it; a loader that can do better for one entry than mapping them all passes `loadOne`, which is what `articles` does to read the hand-picked Related Articles of that one Article. `articles`, `authors` and `tags` all read the same one query, `fetchArticlesAndAuthors` in `entities/queries.ts`, which answers the Articles and the bylines they credit, so the authors collection holds exactly the Authors with a published Article. The steps:

1. `fetchEntries<[RawEntry, …]>(query, …)`: one query per array of raw entries it answers with, in the order they were written, each naming a `collection`, the `references` its mapper reads and, where order matters, an `orderBy` in the database's own names (`publish_date`, `created_at`). The two loaders of the site's chrome are the exception, because what they read is not a collection: `site` calls `fetchSiteSettings()` and `menus` calls `fetchMenu(name)`, from the same module and on the same runtime. That call is the whole of what a loader knows about the CMS: no Effect, no `CmsClient`, no runtime; no page cursor either, so no loader carries a `limit` to buy completeness. Several queries run concurrently because the interface batches them, not because the loader asked, and every matching entry comes back because `fetchEntries` follows the cursor until the collection is exhausted. A `limit` here is therefore an editorial decision (*this page wants the first five*), never a guess at how much content exists
2. map with the concept's DTO, apply domain ordering rules (`sortFavoriteFirst`)
3. key every entry with `identify`, whatever is unique for that concept, *not* automatically the slug: `articles` → `slug`, `tags` → `slug`, `authors` → `slug`, `cities` → `name`, `testimonials` → `quotee`, `projects` → `id` (the one `createProjects` derives from the entry's slug, trimmed, falling back to a slugified name), `menus` → `name`. Each pair is asserted against its loader, and `site` holds one entry, keyed `settings`, since a site has one set of settings. One Author is one Slug in [`GLOSSARY.md`](../../GLOSSARY.md), and the name is a display label. `cities` keeps the name because a City’s slug is `slugify(name)`, so the two are one identity by construction, and `testimonials` keeps the Quotee’s name because a Testimonial has no other identifier and the glossary never promises that one is unique: two quotes from the same person collapse, a cost taken deliberately rather than an id invented for the CMS ([ADR 0019](../../docs/adr/0019-three-questions-before-modelling.md)). `contentLoader` writes the key beside the DTO, `({ id: identify(data), data })`, so a DTO carrying an `id` of its own (`ProjectDTO` does) cannot override the one `identify` chooses
4. `schema` always comes from `@domain/<concept>` and is bound as it is exported, never built, extended or redeclared here. `authors` binds `authorEntrySchema`, which is `authorSchema` plus the `latestArticle` reference (`referenceSchema("articles")`) an authors entry carries beyond the Byline, and `AuthorDTO` is inferred from it, so the field and its type are declared once

The tags loader emits one flat entry per addressable Slug, ordered Article references and all; the A–Z bucketing the tag listing renders is `buildTagIndexBuckets` (`@domain/tag/rules`), called from [`pages/tags/index.astro`](../pages/tags/index.astro).

**Nothing here fetches after the DTO.** The blur placeholder is decoded from the stored blurhash inside `createImage`, so a loader is fetch, map, key.

**Testing a loader.** A loader is reachable from Vitest. [`entities.test.ts`](./entities/entities.test.ts) holds every loader to step 1, and `articles` and `authors` additionally have their own files covering mapping, ordering and the single-entry path. It costs one `vi.mock` per file, which spreads the real `@infrastructure/cms/client` but swaps `CmsClientLive` for the stub layer in [`src/tests/doubles/cmsLayer.ts`](../tests/doubles/cmsLayer.ts), with the raw entries built by [`src/tests/doubles/cmsEntries.ts`](../tests/doubles/cmsEntries.ts). Substitute the layer, never `fetchEntries`: the point is to keep the real runtime and the real batching in the test and replace only EmDash. What `fetchEntries` promises on its own (one array per query, in order, concurrently, and complete however many pages that takes, references included) is asserted once, in [`cms/entries.test.ts`](../infrastructure/cms/entries.test.ts), where `cmsServesPagesOf` makes the double hand out a cursor. ADR 0016 records why the live config itself is out of a unit test's reach.

## Adding a content type

collection in [`seed/seed.json`](../../seed/seed.json) and in each environment's admin → domain concept (`schema`/`types`/`rules`) → `dto/<concept>` → `entities/<plural>` → register the collection in [`src/live.config.ts`](../live.config.ts) → add its tag to `CONTENT_CACHE_TAGS` in [`src/const/contentCache.ts`](../const/contentCache.ts), or a publish in it will not purge the pages that show it. Add the glossary term to `GLOSSARY.md` in the same change.
