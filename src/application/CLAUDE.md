# src/application

The anti-corruption layer between Contentful and the domain. Two halves, `dto/` (mapping) and `entities/` (loading). See ADR 0012 for the layering, and ADR 0002 for why the content is in Contentful at all; this folder is what keeps that choice reversible.

## dto/: Contentful to domain

```
dto/<concept>/
  <concept>DTO.ts   # export function createXs(raw: RawX[]): XDTO[]
  types.ts          # XSkeleton (EntrySkeletonType) + RawX = Entry<XSkeleton, undefined>
  utils/            # mapping helpers owned by this concept
  index.ts          # re-exports the mapper only
```

A mapper is a plain exported function, not an object with a `create` method. There used to be a `BaseDTO<INPUT, OUTPUT, CONFIGURATION>` type every one of them was annotated with; nothing was ever generic over it, no `create` ever took the second argument, and its single-argument shape is what forced a DTO fed by several queries to smuggle them in a positional tuple: `create([rawAuthors, rawArticles])`, where two same-shaped arrays could be swapped without a type error. **A mapper fed by more than one query takes named parameters**: `createAuthors({ rawAuthors, rawArticles })`, `createTagIndex({ rawTags, rawArticles, rawAuthors })`.

- **DTOs are pure on purpose.** They take already-fetched raw entries and return domain DTOs. No `getEntries`, no Effect, no env, no `await` on I/O. Every mapper is synchronous, and deterministic: `formatDate` pins `timeZone: "UTC"` so a publish date does not slide a day backwards when the build runs west of UTC. This is what makes them trivially unit-testable. The line is I/O, not layering. `@infrastructure/images/imageOptimization` *is* imported here, because `getOptimizedImageUrl` and `getOptimizedSrcset` only build a CDN URL string; `getImagePlaceholders`, which fetches, is not.
- **Contentful types stop here.** `EntryFieldTypes`, `EntrySkeletonType`, `documentToHtmlString` may appear in this folder and nowhere downstream. The domain never sees a `sys` or a `fields`.
- **One raw entry, one mapping.** `createAuthor` in `dto/author/utils/author.ts` is the only place a raw author entry becomes Author fields: `createAuthors` spreads it and adds the Latest Article, and `createArticles` calls it for the Byline it embeds. A `utils/` helper normally serves the concept that owns it, and this is the exception: it lives under the concept it maps, not under the one borrowing it, because two hand-copied field lists are what let a Byline and an Author Tag disagree. **Whitespace the CMS kept is trimmed at this boundary too**, so the slug a Byline links to and the slug `/tags/[slug]` is generated from are the same string by construction. A comparison downstream that has to `.trim()` before it matches is a sign a mapping was skipped.
- **One raw entry, one address.** `articleSlug` in `dto/article/utils/reference.ts` is the only place a raw Article entry becomes the string that identifies it, and `articleReference` beside it is the only place one becomes a `Reference<"articles">`. **It throws on an entry with no slug rather than minting one**: `String(undefined)` is `"undefined"`, a reference the consumer (`resolveArticle`) then drops without a word, which is the same silent deletion the trim exists to prevent. No `{ collection: "articles" }` literal is written anywhere else in this folder, and `createArticles` takes its own `slug` from the same call. That is what makes the id the articles collection is keyed on and every reference aimed at it equal *by construction* rather than by four builders happening to agree: the Tag Index, the Author's Articles and an Article's Related Articles all derive from one normalisation. It matters because the consumer, `resolveArticle`/`resolveArticles` in `@modules/core/utils/entries`, drops a reference it cannot find without a word, so a slug Contentful padded used to delete an Article from its own tag pages and empty the Author's Latest Article, at build time, silently.
- **One raw entry, one order.** `dto/article/utils/order.ts` is the only place a raw entry becomes an input to `sortFavoriteFirst`: `toOrderableArticle` builds the `{ reference, isFavorite, publishDateISO }` the rule is typed over, and `orderArticleReferences` is what every caller actually reaches for. The Tag Index and the inferred Related Articles both used to build that carrier object inline, with two different spellings of the date, one of which fed the rule a raw Contentful value where the other fed it a normalised ISO string; `localeCompare` cannot tell you which of the two it got. A date the CMS never set sorts last rather than throwing, and it is this module that decides that.
- **One concept, one decision.** `createRelatedArticles` in `dto/article/utils/articles.ts` is the only module that answers what an Article's Related Articles are. It owns the branch CONTEXT.md defines (hand-picked, else inferred from shared Tags), so `createArticles` hands it the whole batch and takes the answer rather than restating the rule with a ternary. Its inferred branch orders before it caps, through `orderArticleReferences`, so *which* six a reader sees is this module's decision rather than a side effect of the `order` the loader happened to put in its Contentful query. It excludes the Article from its own list in **both** branches, and by `articleSlug`, the same identity every other reference here is built from: an editor who files A under A's own `relatedArticles` gets no card linking back to the page being read, and two Articles that merely share a *title* stay two Articles that can suggest each other. The cap, `INFERRED_RELATED_ARTICLES_LIMIT` (6), applies to the inferred branch only: an Author who picks eight means eight.
- **Derivations delegate to `@domain/<concept>/rules`.** The DTO decides *which* raw field feeds a rule; the rule decides *what the value means*. Don't inline reading-time maths or description trimming here.
- **An asset URL is absolutised here**, by `createImage` in `@application/dto/shared/images`, the one module that knows Contentful serves `//images.ctfassets.net/…`. `imageSchema.url` is therefore an absolute URL and says so, and no page, component or JSON-LD builder re-adds the scheme by hand. A template that does is a leak of exactly the transport detail this layer exists to absorb. The rich-text renderer in `dto/article/utils/content.ts` still prefixes its own embedded-asset URLs, because those come off the raw Contentful node and never reach `createImage`.
- **An internal link is a route, not a string.** The rich-text renderer in `dto/article/utils/content.ts` links an embedded Article with `articleHref` and recognises a tag page with `isTagPath`, both from `@const/routes.ts`, so no hand-written `/articles/` survives in this layer. The canonical-domain test next to them (the base URL an authored link is resolved against to decide whether it is external) is deliberately *not* the site origin `absoluteUrl` uses: it asks whether the editor typed a link to the production domain, which is the same question in every environment, preview included.
- **Optional CMS fields get their defaults at this boundary**, so the domain DTO is total: `?? false` for the editorial flags an author may simply not have ticked, `?? documentToHtmlString(rawArticle.fields.content)` for a description Contentful never received. The body is rendered a second time only for the articles that need it, because `??` never evaluates its right side when a blurb exists. Every default written here is asserted against the DTO layer, so removing one from the code fails the docs test.

## entities/: Astro content collections

```
entities/<plural>/
  <plural>.ts   # defineCollection({ loader, schema })
  index.ts
```

The loader is the only place content I/O happens:

1. `fetchEntries<[Skeleton, …]>(query, …)` takes one query per array of raw entries it answers with, in the order they were written. **A `select` list belongs to the module that reads the fields, not to the loader**: `TAG_INDEX_ARTICLE_FIELDS`, `TAG_INDEX_AUTHOR_FIELDS` and `AUTHOR_LATEST_ARTICLE_FIELDS` are declared next to the functions that consume them and the loader spreads them, so a mapper that starts reading a new field cannot leave the query behind in another file where no type checker relates the two. That drift is what made the Tag Index give up on `RawArticle` and type itself over `Entry<EntrySkeletonType>` instead, buying a file full of `String(article.fields.x)`. That call is the whole of what a loader knows about the CMS: no Effect, no `CmsClient`, no runtime, no credential guard and no page cursor either, so no loader carries a `limit` to buy completeness. Missing credentials answer an empty array per query rather than failing, so builds work without them; several queries run concurrently because the interface batches them, not because the loader asked; and every matching entry comes back because `fetchEntries` pages until the collection is exhausted. A `limit` here is therefore an editorial decision (*this page wants the first five*) rather than a guess at how much content exists
2. map with the concept's DTO, apply domain ordering rules (`sortFavoriteFirst`)
3. attach the blur placeholders with `withImagePlaceholders(field, entries)` (`entities/placeholders.ts`), naming the field that carries the image: `"image"` for most, `"featuredImage"` for Articles, which may not have one. That step is the whole of what a loader knows about placeholders: collect the sources, ask for them at once, put back what came, leave an entry whose source is missing from the answer exactly as it was. It was written out four times before, so the protocol was a four-file edit
4. return entries carrying an `id`: whatever is unique for that concept, *not* automatically the slug. `articles` and `tags` use the slug, `authors` and `cities` the name, `testimonials` the author. `projects` is the one that arrives with its `id` already set, because `createProjects` derives it (`fields.id`, falling back to a slugified name)
5. `schema` always comes from `@domain/<concept>`, never redeclared here. Extending it is the exception: `authors` adds `reference()` fields, which belong at this layer precisely because collection names are not a domain concern

**A collection stores what identifies an entry, never how one page arranges it.** The tags loader emits one flat entry per addressable Slug, ordered Article references and all; the A–Z bucketing the tag listing renders is `buildTagIndexBuckets` in `@domain/tag/rules`, called from `pages/tags/index.astro`. It used to be the stored shape, and both tag routes opened by flattening it back. An arrangement in storage is work every other reader has to undo. It was then a generic `groupBy` in `@shared/utils` with the first-letter half of the rule written as a lambda in the template, which is the same rule in two places and a name that mentioned neither of the two sorts it performed.

Post-processing that *fetches* (`getImagePlaceholders`) happens in the loader, after the mapper rather than inside it. Rewriting an image URL does not fetch, which is why the rich-text renderer in `dto/article/utils/content.ts` may do it inline. Why the fan-out belongs to `getImagePlaceholders` rather than to the loader is `src/infrastructure/CLAUDE.md`; what belongs here is only that a loader reaches for `withImagePlaceholders` and never for a `Promise.all` of its own.

**A collection stores no field no page reads.** An Author used to carry every Article they had written, as an unbounded array of references, so that `about.astro` could read the first one. Nothing else ever touched it, and it cost the loader the whole Article collection on every build plus a second, differently-ordered implementation of "this Author's Articles" sitting next to the one the Tag Index uses. `createAuthors` now derives `latestArticle` and stops there, and the Author Tag's listing stays where it always was, in `dto/tag/utils/tags.ts`. The two orders are not the same and are not meant to be: `CONTEXT.md` says Latest Article is by publish date, while an Author Tag page shows the Blog's Favorite-first order.

**Testing a loader.** A loader is reachable from Vitest. `entities.test.ts` holds every loader to the first step: all six answer with no entries and ask Contentful for nothing without credentials, and all six query once they have them. `articles` and `authors` additionally have their own files covering mapping, ordering and post-processing; the other four do not yet. It costs two `vi.mock` calls per file: one for `astro:content`, and one that spreads the real `@infrastructure/cms/client` but swaps `CmsClientLive` for the stub layer in `src/tests/doubles/cmsLayer.ts`. Substitute the layer, never `fetchEntries`: the point is to keep the real runtime, the real batching and the real `isContentfulConfigured` in the test and replace only the network. What `fetchEntries` promises on its own (one array per query, in order, concurrently, empty without credentials, and complete however many pages that takes) is asserted once, in `cms/entries.test.ts`, where `cmsServesPagesOf` makes the double answer a `total` larger than the items it serves. What the test cannot check is the `schema`: `reference()` has no stand-in, so no entry is ever parsed. ADR 0016 records both halves.

## Adding a content type

domain concept (`schema`/`types`/`rules`) → `dto/<concept>` (a `createXs` function) → `entities/<plural>` → register the collection in `src/content.config.ts`. Add the glossary term to `CONTEXT.md` in the same change.
