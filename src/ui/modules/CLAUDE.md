# src/ui/modules

Feature areas. `about`, `article`, `articles`, `contact`, `home`, `legal`, `projects` map to routes; `core` is everything shared by more than one of them, plus what `src/pages` reaches for directly (`baseLayout`, `head`, `header`, `footer`, `seo`, `jsonLd`, `blurImage`, `cookieConsent`, `themeToggle`, `articleCard`, `breadcrumbs`, `errorLayer`…). **`core` means used by more than one feature, not "generic-looking"**: the form controls sat there while every class they emit was `contact-form__…` and their one variable prop was the contact form's status machine, so a text input in `core` knew that a submission can come back 401. They live under `contact` now, and the prop is `isLocked`.

Imported as `@modules/<feature>/components/<name>/<Component>.astro`.

## Component convention

Every component is a folder holding a co-located pair:

```
<feature>/components/<camelCaseName>/
  <PascalCase>.astro      # or .tsx for a React island
  <kebab-case>.css        # imported by the component: import "./blog.css"
  utils/                  # helpers used only by this component
```

The folder is camelCase, the component PascalCase and the stylesheet kebab-case of the same name. No folder deviates, and the docs test holds it that way. Feature-wide helpers that aren't a component live in `<feature>/utils/` (e.g. `core/utils/jsonLd`), and `about` additionally carries a `hooks/` folder for the one React hook shared inside that feature.

Two wrinkles the shape above doesn't show:

- **No folder carries an `index.ts` barrel.** Every component, React or Astro, is imported by its own path: `@modules/core/components/spinner/Spinner`. There used to be a barrel per React folder, justified as "what lets a React island be imported without the extension the Astro compiler needs". That was never true, since the extensionless path resolves on its own. Four of the seven were dead, and two of those were also broken: they said `export *` for a component exported as `default`, so anyone following the documented convention got `undefined` at runtime, invisible to both Biome and `tsc`.
- **`contact/components/form/` is a grouping folder, not a component.** It holds `input`, `recaptcha` and `textarea` plus a `shared.css` the three of them `@import` from their own stylesheets. That is the only shared stylesheet in the tree; reach for it only if you are adding a fourth form control.

A component used in more than one place is parameterised by a class, never copied per placement. The sliders are the worked example: `core/components/sliderShell/SliderShell.astro` is the track, its buttons and its dots, `core/components/articleSlider/ArticleSlider.astro` is the one module that turns Articles into slides, and its three callers (`LatestArticles`, `AboutLatestArticles` and `RelatedArticles`) differ only in the class they hand it. Everything that varies (`--slides-per-view`, `--slider-gap`, the grid area, the button treatment) is a rule on that class in the calling section's own stylesheet, so a new placement is a class and a few declarations, not a folder. `TestimonialsSlider` talks to `SliderShell` directly because Testimonials are not Articles, and it is the only caller that asks for dots.

**There is one answer to "next slide", and it is `sliderShell/utils/slider.ts`.** `initSlider` tracks which slide sits nearest the track's centre, and moves a dot's target into view by centring it. How the arrows move is the caller's one choice: by default it pages by the width of the track and clamps at both ends by disabling the button, which is what a slider showing four Articles wants; `isLooping` steps one slide at a time and wraps, which is what a slider showing one Testimonial wants. **The module sets both buttons' `disabled` on every update rather than trusting the markup**, because the server renders `prev` disabled and a looping slider would otherwise start with a button nothing ever enables. `TestimonialsSlider` used to opt out with `hasButtons={false}` and then rebuild all of that beside the shell: its own arrows, its own dots, its own active-index tracking, and a *different* scroll model (centre-and-wrap against the shell's page-and-clamp). Two answers to one question in two files, while this guide claimed there was one. The dots are ordinary buttons: they were `::scroll-marker` for a while and every caller turned them off, which ADR 0009 now records.

Every bundled `<script>` in the tree is one line: an `astro:page-load` listener delegating to a `utils/` module. There are no exceptions, and the docs test holds the initialisers to it. A bundled `<script>` initialises on `astro:page-load`, never at module scope. **Neither does the module it imports.** A listener registered at the top level of a `utils/` file runs once per session rather than once per page, which looks like it works and is what the rule exists to prevent: it survives a swap by accident, and it makes the component's wiring unfindable from the component. `initReadingProgress` and `initializeColumnsToggle` register their own listeners, and `watchBackground` registers the header's; a re-run is a no-op because the callback is a named module-level function, which is what the browser deduplicates on. Where the callback has to close over the page's own elements it cannot be deduplicated that way, so `initMenu` keeps an `AbortController` and drops the previous run's document-level listeners before registering its own. Otherwise Escape would fire once per navigation ever made, each time against a button that is no longer in the document. `ClientRouter` is rendered on every page, and it runs a given script **once per session**: `deselectScripts` stamps `data-astro-exec` on any script it has already seen, so on the second navigation the swapped-in body is never wired. The event fires on the initial load too, so deferring costs nothing and is what makes the wiring survive a swap, which is also why the initialiser must be idempotent, since it re-runs on every navigation. Every scripted component in the tree does this and the docs test holds them to it; the bug it prevents is invisible to `tsc`, Biome, the unit suite, `astro check` and the build alike, because all five only ever see the first pageview. `is:inline` scripts are exempt: they are not bundled, and the two that matter have to run before paint (ADR 0005, ADR 0013). Neither is written in `Head.astro`: `THEME_BOOTSTRAP_SCRIPT` and `consentBootstrapScript` are built by the modules that own the storage keys and the category names, and `Head.astro` renders them with `set:html` and nothing else. `define:vars` may not be added beside `set:html` on those tags, because Astro drops the `set:html` content when both are present and the page then ships an empty script that fails silently.

## Styling

- **Component CSS is not scoped by Astro.** It is a plain global stylesheet imported next to the component, so the class names are the only isolation there is. Namespace with a block class named after the component and BEM elements under it: `.blog`, `.blog__inner`, `.article-card__byline`. Not one component uses an Astro `<style>` block, and the docs test keeps it that way: a `<style>` block *would* be scoped, so a single one would make "the class names are the only isolation" quietly false for the next reader.
- **Modifiers are BEM modifiers** (ADR 0014): `block--modifier` or `block__element--modifier`, fused into a single class (`.contact-tab--active`, `.contact-form__submit--loading`, `.article-card__item--landscape`). No standalone `.--modifier` classes, and no `is-`/`has-` prefixes: that is SMACSS vocabulary, not BEM. A modifier is also never a bare descendant standing in for one (`.card .active`): the block goes on the element too, even where it carries no rules, as `.columns-toggle__label--single` does.
- **Cross-block behaviour is a block, mixed in**, applied alongside the component's own block as a BEM *mix*: `class="navigation__menu__link underline-on-hover clickable"`. The mixes live in two files under `@styles/global`, and which one is decided by cascade layer rather than by subject matter: behavioural mixes in `modifiers.css` (`@layer modifiers`), typographic and layout ones in `global.css` (`@layer global`). Component stylesheets are unlayered, so they beat both without extra specificity, and a block may override a mix for itself: `menu.css` paints `.navigation__menu__link.current-page` gold rather than the `--primary-main` the mix gives it. Reach for one of the behavioural mixes before inventing a per-block duplicate:
	- `underline-on-hover`: a link or link-like button that underlines on hover
	- `clickable`: anything that responds to a press
	- `inverted-color-scheme`: a section that inverts against the page, and the header's cue to invert its logo and menu button over it
	- `current-page`: the entry pointing at the route already being viewed
	- `item-wrapper`: a list item whose card link stretches over the whole item
	- `visually-hidden`: an element the design hides but a screen reader and the tab order must still reach. The theme toggle's checkbox was `display: none`, which takes a control out of both, so the theme could not be changed by keyboard at all
- **State owned by the page is a `page` modifier.** Anything that flips several unrelated blocks at once hangs off `<html>` and is consumed by descent, not by tagging each element: `.page--menu-open .reading-progress { … }`. See `@styles/CLAUDE.md`.
- Consume tokens and shared utilities from `@styles` (`var(--font-size-h3)`, `var(--rhythm)`, `.editorial-headline`, `.reveal`, `.underline-on-hover`). Don't reinvent typography.
- Prefer container queries against the page container declared in `styles/base/base.css` (`@container home-page (width <= 960px)`) over viewport media queries.
- A style that only this component uses never goes into `@styles/global`, which is for genuinely cross-cutting rules.

## Islands

React is used only where interaction demands it: `about/worldGlobe` (three / react-globe.gl), `contact/contactForm` + `contactFormProvider` (react-hook-form), `core/cookieConsent`, `contact/form/*`, `core/spinner`. Everything else is `.astro`, rendered on the server.

Writing a React component does not create an island. There are only three hydration roots in the whole site: `WorldGlobe` in `LittleMoreOfMe.astro`, `ContactFormProvider` in `Tabs.astro` and `CookieConsent` in `Footer.astro`. `WorldGlobe` and `CookieConsent` are `client:only="react"` because neither survives a server render: `WorldGlobe` reads `window.innerWidth` in a `useState` initialiser and `CookieConsent` mounts `vanilla-cookieconsent`, which is browser-only. `ContactFormProvider` is `client:load` and does survive one: the rule is not which hooks a component calls but whether anything in its render path dereferences a browser global, and a `useState` initialiser is render. That is the whole difference between the two, which matters because it is the only island whose markup a reader needs before JavaScript arrives: under `client:only` the contact page served no `<form>`, no `<input>` and no `<textarea>` at all, so the site's one conversion path was a heading above an empty box until React landed. It does **not** make the form work without JavaScript, and the attempt is worth recording so nobody repeats it: an Astro action reached from an HTML form needs `?_action=<name>` on an on-demand page, because `/_actions/<name>` is the RPC route and answers a form POST with raw JSON. Wiring that correctly still fails, because `contactFormSchema` requires a `recaptcha` token and reCAPTCHA v3 mints it in the browser, so a native POST can only ever answer "Mr. Robot, is that you?". The markup is server-rendered so a reader sees and can fill the form immediately; submitting it is React's job and will stay React's job while the token is mandatory. The other React files are children of those three and hydrate with their root. So an island costs a hydration directive at a call site, which is the moment to ask whether CSS or an Astro component would do (ADR 0009).

**A card is handed a projection, not the entry the page happened to have.** `ArticleCard` took `CollectionEntry<"articles"> & { isLandscape?: boolean }` and was called with a spread, which put a presentational flag in the same namespace as every CMS field: adding `isLandscape` to `articleSchema` would have collided silently, one of the two winning. It also re-spread the whole rendered article body as props for a card that prints a 200-character description. `toArticleCardContent` in that component's `utils/` names what a card is, including the four-tag cap and the overflow count that used to be computed in the template, and the component takes `article` and `isLandscape` as two separate props.

An island's props are also its payload: `client:only` serializes them into the page's HTML so the browser can hand them back on hydration, which makes a prop a projection of what the component actually reads rather than the `CollectionEntry` the page happened to have. `toCityPoints` in `about/utils/globe.ts` maps cities down to the `CityPoint` the globe needs (coordinates, name, the City's Slug), so the descriptions and the base64 image placeholders `Cities.astro` renders beside it are not shipped a second time for a globe that never looks at them. The projection lives beside the type it builds, not in `LittleMoreOfMe.astro`'s frontmatter: a template is the one place a test cannot reach, and it stays out of the ACL because `lat`/`lng`/`label` are `react-globe.gl`'s accessor names rather than the domain's: the collection says `coordinates.latitude` and `name`, and a second consumer, `Cities.astro`, needs the fields the globe drops. The Slug travels rather than being re-derived in the browser: it is what `Cities.astro` puts on the card's `id`, and what a pin scrolls to. A prop that cannot survive that trip is bound *inside* the island instead: `ContactForm`'s `submit` and `getRecaptchaToken` are functions, so `ContactFormProvider` builds them in the browser and passes them down, and the hydration root itself keeps taking none.

## Data

Components read content through `getCollection`/`getEntry` from `astro:content`, never by calling Contentful or `@infrastructure` directly; the docs test fails on either import anywhere under `src/ui`. Dereferencing a stored `reference()` is `resolveArticle` / `resolveArticles` in `core/utils/entries.ts` and only that, for one reference or a list of them, and `getEntry` is called nowhere else under `src/ui` or `src/pages`. The pair drops what no longer exists rather than answering a hole, keeps the order the collection stored, and answers a plain promise, so no caller writes its own `getEntry` fan-out, re-sorts what comes back, grafts a resolved entry onto the entity that referenced it, or reaches for Effect to await one entry. Nothing under `src/ui` imports `effect` at all, which is the promise ADR 0004 makes about the read path. `RelatedArticles.astro` and the tag route resolve a list, and the ordering they show is the one `sortFavoriteFirst` decided upstream; `about.astro` resolves the single Latest Article the Author carries. Server mutations go through the generated `astro:actions` client, not through `@actions` itself: nothing here imports that alias, and `actions.contact` is the only mutation in the tree. It is bound in `ContactFormProvider.tsx` (which reaches `astro:actions` and reCAPTCHA) and handed to `ContactForm.tsx` as the `submit` and `getRecaptchaToken` props, so the form imports nothing from `astro:*` and its status machine is asserted in the dom project (ADR 0016). What `submit` answers is a `ContactSubmission` from `contact/utils/submission.ts`, not the action's own result: the form reads the 401 that locks it out, and an answer that is neither ok nor an error is undelivered rather than silent. `getRecaptchaToken` is **absent, not failing, while reCAPTCHA is still loading**: the provider hands the prop down only once `executeRecaptcha` exists, and a submit with no verifier waits instead of proceeding. Collapsing the two into one function that answers `undefined` is what turns "the script has not loaded yet" into "you are a bot": a legitimate visitor who submits quickly gets accused, which is the one failure this seam has already produced once.

A link to content is not spelled here either. `articleHref`, `tagHref` and `projectHref` in `@const/routes.ts` turn a Slug into a path, and `absoluteUrl` folds in the origin, no component reads `SITE_URL` or joins `PAGES_ROUTES` to a slug of its own, and none reads `Astro.site` either, which used to give the canonical and OG tags a second origin the JSON-LD could disagree with. **The JSON-LD list builders take slugs, not URLs**: `buildArticleListSchema`, `buildProjectListSchema` and `buildTagListSchema` in `core/utils/jsonLd.ts` own the `absoluteUrl(articleHref(slug))` composition that was written out at nine call sites. What carries a schema into the document is `core/components/jsonLd/JsonLd.astro` and only that, so the `<script is:inline type="application/ld+json">` tag is written once rather than fourteen times.

An image is passed whole, not unpacked. `BlurImage` takes `image={…}`, the `imageSchema` shape every content type shares, and reads `url`, `details` and `placeholder` itself. Seven call sites used to write the same four-line unpack, which meant every one of them had to know the schema's internal nesting to satisfy a component that could simply be handed the object. The one derivation that used to live in a template, the Featured Article's share intents, is `buildArticleShareLinks` under that component's `utils/`, where a test can reach it.

Bianca's email address is owned the same way, by `core/components/emailButton`. `EmailButton.astro` takes a `label`, or `shows="address"`, and never the address itself: the server renders the placeholder `our email address`, and `activateEmailButtons` in that component's `utils/interactions.ts` decodes `CONTACT_DETAILS.ENCODED_EMAIL_BIANCA` in the browser, to fill the text in, and to open the composer on a click. So the address is never server-rendered, which is the whole point of the base64 and the thing the two legal pages used to defeat by decoding it themselves in their frontmatter. The class the listener matches is declared once, in that module, and the template, `email-button.css` and the listener all read it from there: a behavioural selector spelled twice is what left every Email button on the site inert, because two string literals meant to be the same one are invisible to both Biome and `tsc`. The listener answers a trusted click only, so a script cannot dispatch its way to the address.

The Contact page's `?tab=` deep link is owned the same way, by `contact/utils/tabs.ts`. The query key is declared there beside the tab ids, `initTabs` reads it off the page's own URL, and the `astro:page-load` script in `Tabs.astro` hands it nothing, so the half that reads the deep link and the half that writes it cannot spell the key differently, the drift that left every Email button inert. That module also keeps the two directions apart: restoring the tab a URL asks for only applies it and touches no history at all, while a reader's click publishes it as a `replaceState`, a view change on the same page, not a navigation, carrying the router's own `history.state` rather than a fresh one. Restoring used to push an entry instead, which trapped the reader: Back returned to the un-suffixed URL, `ClientRouter` re-ran `astro:page-load`, and the tab was pushed again.

What "the reader's theme" means is owned by `core/components/themeToggle`, and it is two things rather than one. `const.ts` declares the storage key, the `data-theme` attribute and the vocabulary: a **preference**, `dark`, `light` or `system`, and the theme actually painted, which `utils/preference.ts` resolves from that preference and `prefers-color-scheme`. Nothing stored, or anything unrecognised, reads as `system`. Only a click on the toggle persists: `utils/theme.ts` paints without writing, and its `prefers-color-scheme` listener applies a change only while the preference is `system`. That split is what keeps both halves of the behaviour honest, mirroring the OS at midday no longer stores `light` as if the reader had chosen it (which used to make "follows the operating system" true for the first pageview only), and an OS switching to dark under a reader who asked for light no longer repaints mid-read and overwrites the choice. The render-blocking bootstrap is the same rule, and the same module builds it: `Head.astro` renders `THEME_BOOTSTRAP_SCRIPT` with `set:html` on the `is:inline` tag ADR 0005 requires, so the key, the attribute and the fallback are never restated as literals in a template that neither Biome nor `tsc` reads.

Whether a page shows its chrome at all is the same kind of decision, and it is `siteChrome` in `core/utils/siteChrome.ts`: the only reader of `HIDE_CHROME` in the tree, answering `showsHeader`, `showsBreadcrumbs`, `showsTableOfContents` and `servesRealContent` for a URL. `BaseLayout.astro` asks it whether to render the `Header` and whether to serve the `<slot />` or the under-construction placeholder, the Article route asks it about the Table of Contents, and `Breadcrumbs.astro` asks it about itself, which is why every call site renders it unconditionally and none of them can hide it on one route and forget on the next. Deny by default: a route is served for real only if it is under one of the published routes `siteChrome` names, so a new page inherits the placeholder rather than the exemption.
