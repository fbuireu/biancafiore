# src/ui/modules

Feature areas. `about`, `article`, `articles`, `contact`, `home`, `legal`, `projects` map to routes; `core` holds the layout and the chrome it renders (`head`, `seo`, `header`, `footer`, `cookieConsent`, `themeToggle`, `scrollTop`…), what [`src/pages`](../../pages) imports directly (`baseLayout`, `breadcrumbs`, `errorLayer`, `articleCard`, `relatedArticles`, `latestArticles`, `emailButton`, `jsonLd`…) and what more than one feature shares (`sliderShell`, `articleSlider`, `blurImage`, `socialNetworks`). `linkWithArrow` and `spinner` are the exceptions, with one caller each, in `articles` and `contact`.

Imported from outside its feature as `@modules/<feature>/components/<name>/<Component>.astro`, and by relative path from inside it.

## Component convention

Every component is a folder holding a co-located pair:

```
<feature>/components/<camelCaseName>/
  <PascalCase>.astro      # or .tsx for a React island
  <kebab-case>.css        # imported by the component: import "./blog.css"
  utils/                  # helpers used only by this component
```

The folder is camelCase, the component PascalCase, the stylesheet kebab-case of the same name: no folder deviates, and the docs test holds it that way. Feature-wide helpers that aren't a component live in `<feature>/utils/` (e.g. `core/utils/jsonLd`), and `about` additionally carries a `hooks/` folder for `useTabVisibility`, the one custom React hook in the tree, which only the globe reads.

Wrinkles the shape above doesn't show:

- **A React component is imported by its path without an extension** (`@modules/core/components/spinner/Spinner`), an Astro component by its full `.astro` path. No folder carries an `index.ts` barrel.
- **[`contact/components/form/`](./contact/components/form) is a grouping folder, not a component.** It holds `input`, `recaptcha` and `textarea` plus a [`shared.css`](./contact/components/form/shared.css) they all `@import` from their own stylesheets. That is the only shared stylesheet in the tree; reach for it only if you are adding a further form control.

The sliders share one track. [`core/components/sliderShell/SliderShell.astro`](./core/components/sliderShell/SliderShell.astro) is the track and its buttons, [`core/components/articleSlider/ArticleSlider.astro`](./core/components/articleSlider/ArticleSlider.astro) is the one module that turns Articles into slides, and its callers (`LatestArticles`, `AboutLatestArticles`, `RelatedArticles`) differ only in the class they hand it, bar `RelatedArticles`, which also passes `isShuffled`. Everything that varies (`--slides-per-view`, `--slider-gap`, the grid area, the button treatment) is a rule on that class in the calling section's own stylesheet. `TestimonialsSlider` talks to `SliderShell` directly because Testimonials are not Articles, and it is the only caller that loops (`isLooping`) and shows dots (`hasDots`), which move its buttons into the dot navigation.

A bundled `<script>` initialises on `astro:page-load`, never at module scope. **Neither does the module it imports.** A listener registered at the top level of a `utils/` file runs once per session rather than once per page, which looks like it works: it survives a swap by accident, and it makes the component's wiring unfindable from the component. The docs test holds both halves: the shape of every bundled `<script>`, and the absence of any module-scope listener or `matchMedia` read in the `utils/` modules they import. `ClientRouter` is rendered on every page, and it runs a given script **once per session**: `deselectScripts` stamps `data-astro-exec` on any script it has already seen, so on the second navigation the swapped-in body is never wired. The event fires on the initial load too, so deferring costs nothing. The swap replaces `<body>` and keeps `window`, `document` and the `<html>` element: the initialiser re-runs on every navigation, so what it adds to those three must not stack. The bug is invisible to `tsc`, Biome, the unit suite, `astro check` and the build alike, because every one of them only ever sees the first pageview. `is:inline` scripts are exempt: they are not bundled, and the two that matter, the theme bootstrap and the consent gate in [`Head.astro`](./core/components/head/Head.astro), have to run before paint (ADR 0005, ADR 0013).

The Article page's modules lean on markup the route and the renderer produce. `ColumnsToggle` and `ReadingProgress` find the body by `.article-wrapper` and paint nothing without it, and the `article-wrapper--two-columns` the toggle sets is styled only in `_article.css`. `TableOfContents` highlights the section being read: each entry animates on `--for`, the `scope` the renderer stamps on that heading's `<section>` as `--is`, which `_article.css` turns into a view timeline and lifts to `.article-wrapper` through the `--scopes` list the route writes. No unit test reads those files together, so a rename on one side stops the toggle, the bar or the highlight without failing the suite.

## Styling

- **Component CSS is not scoped by Astro**: it's a plain global stylesheet imported next to the component, so the class names are the only isolation there is. Not one component uses an Astro `<style>` block, and the docs test keeps it that way: a `<style>` block *would* be scoped, so a single one would make "the class names are the only isolation" quietly false for the next reader.
- **Cross-block behaviour is a block, mixed in**, applied alongside the component's own block, a BEM *mix*: `class="navigation__menu__link underline-on-hover clickable"`. The mixes live in two files under `@styles/global`, split by cascade layer: behavioural mixes in [`modifiers.css`](../styles/global/modifiers.css) (`@layer modifiers`), typographic and layout ones in [`global.css`](../styles/global/global.css) (`@layer global`). Component stylesheets are unlayered, so they beat both without extra specificity, and a block may override a mix for itself: [`menu.css`](./core/components/header/atoms/menu/menu.css) paints `.navigation__menu__link.current-page` gold rather than the `--primary-main` the mix gives it. The behavioural mixes:
	- `underline-on-hover`: a link or link-like button that underlines on hover
	- `clickable`: anything that responds to a press
	- `inverted-color-scheme`: a section that inverts against the page, and the header's cue to invert its logo and menu button over it
	- `current-page`: the entry pointing at the route already being viewed
	- `item-wrapper`: a list item whose card link stretches over the whole item
	- `visually-hidden`: an element the design hides but a screen reader and the tab order must still reach, such as the theme toggle's checkbox; `display: none` takes a control out of both
- Component CSS queries the container [`styles/base/base.css`](../styles/base/base.css) names for its page (`@container home-page (width <= 960px)`); the styles guide says which routes get one.

## Islands

The React components: `about/worldGlobe` (three / react-globe.gl), `contact/contactForm` (react-hook-form) + `contactFormProvider` (reCAPTCHA), `contact/form/*`, `core/cookieConsent`, `core/spinner`. Everything else is `.astro`, rendered on the server. `astro.config.ts` compiles them with the React Compiler (`react({ compiler: true })`), which memoises every component and hook itself.

Writing a React component does not create an island. There are only three hydration roots in the whole site: `WorldGlobe` in [`LittleMoreOfMe.astro`](./about/components/littleMoreOfMe/LittleMoreOfMe.astro), `ContactFormProvider` in [`Tabs.astro`](./contact/components/tabs/Tabs.astro), `CookieConsent` in [`Footer.astro`](./core/components/footer/Footer.astro). Every one is hydrated the earliest way it can be, which is not the same directive for all three. `CookieConsent` is `client:only="react"`: its one control does nothing until `vanilla-cookieconsent` runs in the component's effect, so the server renders nothing for it. `WorldGlobe` is `client:load` even though its inner component reads `window.innerWidth` in a `useState` initialiser: the root wraps it in `<Suspense>` and the inner component opens with `use(browser())` from `react-dom`, so the server emits the fallback, an `<aside>` of the canvas's height, and the browser renders the rest on hydration without a recoverable error. That is what puts the reserved height in the HTML instead of leaving the island empty until its script runs. `ContactFormProvider` is also `client:load`, so the form is server-rendered and hydrated on load, which it can afford because `react-google-recaptcha-v3`'s provider renders its children either way and `useGoogleReCaptcha` simply has no `executeRecaptcha` until the script is in: the same absence the `getRecaptchaToken` prop already models below. The other React files are children of those and hydrate with their root.

A hydration directive serializes an island's props into the page's HTML. `toCityPoints` in [`about/utils/globe.ts`](./about/utils/globe.ts) maps cities down to the `CityPoint` the globe needs (coordinates, name, the City's Slug): `lat`/`lng` are `react-globe.gl`'s default accessor names and `label` is what the pin prints, not the domain's names, and [`Cities.astro`](./about/components/cities/Cities.astro), the second consumer, needs the fields the globe drops. The Slug travels rather than being re-derived in the browser: it is what `Cities.astro` puts on the card's `id`, and what a pin scrolls to. The countries file the globe fetches is checked rather than trusted: [`worldGlobe/utils/countries.ts`](./about/components/worldGlobe/utils/countries.ts) checks [`public/countries.json`](../../../public/countries.json) against a zod schema (a `features` list of GeoJSON `Feature`s with `Polygon` or `MultiPolygon` geometry) and answers an empty list for anything else, so an unreadable or reshaped file draws an empty globe. `ContactForm`'s `submit` and `getRecaptchaToken` are functions, which cannot survive that trip, so `ContactFormProvider` binds them in the browser and passes them down, and the hydration root itself takes none.

## Data

Components read content through `getCollection`/`getEntry` from `astro:content`, never by calling Contentful or `@infrastructure` directly: the docs test fails on either import anywhere under [`src/ui`](..). Dereferencing a stored `reference()` is `resolveArticle` / `resolveArticles` in [`core/utils/entries.ts`](./core/utils/entries.ts) and only that: one reference or a list of them, and `getEntry` is called nowhere else under `src/ui` or `src/pages`. The pair drops what no longer exists rather than answering a hole, keeps the order the collection stored, and answers a plain promise, so no caller writes its own `getEntry` fan-out, re-sorts what comes back, grafts a resolved entry onto the entity that referenced it, or reaches for Effect to await one entry; nothing under `src/ui` imports `effect` at all, which is the promise ADR 0004 makes about the read path. [`RelatedArticles.astro`](./core/components/relatedArticles/RelatedArticles.astro) and the tag route resolve a list: the tag route shows the order `sortFavoriteFirst` decided upstream, and `RelatedArticles` shuffles its slides at build time through `ArticleSlider`'s `isShuffled`; [`about.astro`](../../pages/about.astro) resolves the single Latest Article the Author carries. Server mutations go through the generated `astro:actions` client, never by importing `src/actions`, and `actions.contact` is the only mutation in the tree. It is bound in [`ContactFormProvider.tsx`](./contact/components/contactFormProvider/ContactFormProvider.tsx) (which reaches `astro:actions` and reCAPTCHA) and handed to [`ContactForm.tsx`](./contact/components/contactForm/ContactForm.tsx) as the `submit` and `getRecaptchaToken` props, so the form imports nothing from `astro:*` and its status machine is asserted in the dom project (ADR 0016). What `submit` answers is a `ContactSubmission` from [`contact/utils/submission.ts`](./contact/utils/submission.ts), not the action's own result: the form reads the 401 that locks it out, and an answer that is neither ok nor an error is undelivered rather than silent. `getRecaptchaToken` is **absent, not failing, while reCAPTCHA is still loading**: the provider hands the prop down only once `executeRecaptcha` exists, and a submit made before then does nothing: it neither sends nor accuses. Collapsing the two into one function that answers `undefined` is what turns "the script has not loaded yet" into "you are a bot": a legitimate visitor who submits quickly gets accused.

`articleHref` and `tagHref` in [`@const/routes.ts`](../../const/routes.ts) turn a Slug into a path, `projectHref` turns a Project's `id` into an anchor on `/projects`, and the JSON-LD builders in [`core/utils/jsonLd.ts`](./core/utils/jsonLd.ts) take Slugs, ids or paths and call `absoluteUrl` themselves. The Featured Article's share intents are `buildArticleShareLinks` under that component's `utils/`. What a tag route calls itself is owned by `tagPageCopy` in [`core/utils/tagPage.ts`](./core/utils/tagPage.ts): it reads the stored `type` and names an Author rather than hashing their slug, which is the only thing in the tree that reads that discriminant after the tag index sets it.

Bianca's email address is owned by [`core/components/emailButton`](./core/components/emailButton). [`EmailButton.astro`](./core/components/emailButton/EmailButton.astro) takes a `label`, or `shows="address"`, and never the address itself: the server renders the placeholder `our email address`, and `activateEmailButtons` in that component's [`utils/interactions.ts`](./core/components/emailButton/utils/interactions.ts) decodes `CONTACT_DETAILS.ENCODED_EMAIL_BIANCA` in the browser: to fill the text in, and to open the composer on a click. So the address is never server-rendered, which is the whole point of the base64. The class the listener matches, `EMAIL_BUTTON_CLASS`, lives in [`const.ts`](./core/components/emailButton/const.ts): declared once, in that module, which the template and the listener import, while [`email-button.css`](./core/components/emailButton/email-button.css) spells it again and the docs test holds the two equal. The listener answers a trusted click only, so a script cannot dispatch its way to the address.

The Contact page's `?tab=` deep link is owned by [`contact/utils/tabs.ts`](./contact/utils/tabs.ts). The query key is declared there beside the tab ids: `activeTab` reads it for the server render, which sees the query string only because `contact.astro` renders on demand, `initTabs` reads it off the page's own URL, and the `astro:page-load` script in `Tabs.astro` hands it nothing, so the halves that read the deep link and the half that writes it cannot spell the key differently. That module also keeps the two directions apart: restoring the tab a URL asks for only applies it and touches no history at all, while a reader's click publishes it as a `replaceState` (a view change on the same page, not a navigation), carrying the router's own `history.state` rather than a fresh one. A restore that pushed an entry would trap the reader: Back would return to the un-suffixed URL, `ClientRouter` would re-run `astro:page-load`, and the tab would be pushed again. [`e2e/contact-tabs.spec.ts`](../../../e2e/contact-tabs.spec.ts) finds the page by `.contact-tab` and skips itself when there is none, so renaming that block switches the spec off instead of failing it. The requested tab id, a clicked tab's `data-target` and the `Calendly` global are checked against zod schemas in that module: an unknown tab id falls back to the first tab or is ignored, and a `Calendly` global that is not the vendor's object makes the module load the vendor script rather than call it.

**zod reaches the browser only where it is already paid for.** `astro/zod` bundles to a shared chunk of about 25 KB gzipped, which `/contact` loads anyway for `ContactForm`'s resolver and the lazily loaded globe canvas takes on top of `three`. A browser module anywhere else checks what it reads by literal comparison instead: the stored theme preference (`readPreference`) and the Green Web Foundation answer (`isGreenHost`, which believes only `green === true`) on every page, and the stored columns flag (`isColumnsEnabled`) on every Article, would each pay that chunk for one yes or no, and the `is:inline` scripts in `Head.astro` cannot import at all. [`CarbonBadge.astro`](./core/components/carbonBadge/CarbonBadge.astro) runs `renderCarbonBadge` from its [`utils/carbon.ts`](./core/components/carbonBadge/utils/carbon.ts), and its template reads the badge's id, `BADGE_ID`, from the same module.

What "the reader's theme" means is owned by [`core/components/themeToggle`](./core/components/themeToggle), and it is two things rather than one. [`const.ts`](./core/components/themeToggle/const.ts) declares the storage key, the `data-theme` attribute and the vocabulary: a **preference** (`dark`, `light` or `system`) and the theme actually painted, which [`utils/preference.ts`](./core/components/themeToggle/utils/preference.ts) resolves from that preference and `prefers-color-scheme`. Nothing stored, or anything unrecognised, reads as `system`. Only a click on the toggle persists: [`utils/theme.ts`](./core/components/themeToggle/utils/theme.ts) paints without writing, and its `prefers-color-scheme` listener applies a change only while the preference is `system`. So mirroring the operating system stores nothing, and an operating-system switch under a reader who chose a theme repaints nothing. The render-blocking bootstrap is the same rule, and the same module builds it: `Head.astro` renders `THEME_BOOTSTRAP_SCRIPT` with `set:html` on the `is:inline` tag ADR 0005 requires, so the key, the attribute and the fallback are never restated as literals in a template that neither Biome nor `tsc` reads. `theme.ts` also paints the incoming document on `astro:before-swap`, because the swap replaces the attributes of `<html>` with the incoming document's, which carries no `data-theme`.

Whether a page shows its chrome at all is `siteChrome` in [`core/utils/siteChrome.ts`](./core/utils/siteChrome.ts): the only reader of `HIDE_CHROME` in the tree, answering `showsHeader`, `showsBreadcrumbs`, `showsTableOfContents` and `servesRealContent` for a URL. [`BaseLayout.astro`](./core/components/baseLayout/BaseLayout.astro) asks it whether to render the `Header` and whether to serve the `<slot />` or the under-construction placeholder, the Article route asks it about the Table of Contents, and [`Breadcrumbs.astro`](./core/components/breadcrumbs/Breadcrumbs.astro) asks it about itself, which is why every call site renders it unconditionally and none of them can hide it on one route and forget on the next. Deny by default: a route is served for real only if it is under one of the published routes `siteChrome` names, so a new page inherits the placeholder rather than the exemption.
