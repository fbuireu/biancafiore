# src/ui/modules

Feature areas. `about`, `article`, `articles`, `contact`, `home`, `legal`, `projects` map to routes; `core` holds the layout and the chrome it renders (`head`, `seo`, `header`, `footer`, `cookieConsent`, `themeToggle`, `scrollTop`…), what [`src/pages`](../../pages) imports directly (`baseLayout`, `breadcrumbs`, `errorLayer`, `articleCard`, `relatedArticles`, `blogPreview`, `emailButton`, `jsonLd`…) and what more than one feature shares (`sliderShell`, `articleSlider`, `blurImage`, `socialNetworks`). A component that a single other feature reads, and that no `core` component or page reads, lives in that feature (`articles/linkWithArrow`, `contact/spinner`), and the docs test holds the line.

Imported from outside its feature as `@modules/<feature>/components/<name>/<Component>.astro`, and by relative path from inside it.

## Component convention

Every component is a folder holding a co-located pair:

```
<feature>/components/<camelCaseName>/
  <PascalCase>.astro      # or .tsx for a React island
  <kebab-case>.css        # imported by the component: import "./blog.css"
  utils/                  # helpers used only by this component
```

The folder is camelCase, the component PascalCase, the stylesheet kebab-case of the same name: no folder deviates, and the docs test holds it that way. A helper that two components or a page read lives in `<feature>/utils/` (e.g. `core/utils/jsonLd`), while one that a single component reads lives in that component's own `utils/` (`contact/components/tabs/utils/tabs.ts`, `core/components/baseLayout/utils/page.ts`), and the docs test holds both halves. `about` additionally carries a `hooks/` folder for `useTabVisibility`, the one custom React hook in the tree, which only the globe reads.

Wrinkles the shape above doesn't show:

- **A React component is imported by its path without an extension** (`../spinner/Spinner`), an Astro component by its full `.astro` path. No folder carries an `index.ts` barrel.
- **[`contact/components/form/`](./contact/components/form) is a grouping folder, not a component.** It holds `input`, `recaptcha` and `textarea` plus a [`shared.css`](./contact/components/form/shared.css) they all `@import` from their own stylesheets. That is the only shared stylesheet in the tree; reach for it only if you are adding a further form control.

The sliders share one track. [`core/components/sliderShell/SliderShell.astro`](./core/components/sliderShell/SliderShell.astro) is the track and its buttons, [`core/components/articleSlider/ArticleSlider.astro`](./core/components/articleSlider/ArticleSlider.astro) is the one module that turns Articles into slides, and its callers (`BlogPreview`, `AboutBlogPreview`, `RelatedArticles`) differ only in the class they hand it. `ArticleSlider` owns the scroll reveal of its slides, in `article-slider.css`: `.article-slider` names a view timeline that each slide's `.reveal` follows in place of its own, and each slide numbers itself for the stagger. Everything that varies (`--slides-per-view`, `--slider-gap`, the grid area, the button treatment) is a rule on that class in the calling section's own stylesheet. The slider's default ramp is in `slider.css`, so a placement states only the steps that differ: `RelatedArticles` and `BlogPreview` add a third or fourth slide from 1024px, and `AboutBlogPreview` keeps one slide to 1024px, which is why it restates the first step for the range between. `TestimonialsSlider` talks to `SliderShell` directly because Testimonials are not Articles, and it is the only caller that loops (`isLooping`) and shows dots (`hasDots`), which move its buttons into the dot navigation. A wrapper without dots carries the `slider-wrapper--buttons` modifier, which lays the buttons out beside the track; the variant is a class because a stylesheet reads it, while `data-is-looping` stays an attribute because only the script does.

A bundled `<script>` initialises on `astro:page-load`, never at module scope. **Neither does the module it imports.** A listener registered at the top level of a `utils/` file runs once per session rather than once per page, which looks like it works: it survives a swap by accident, and it makes the component's wiring unfindable from the component. The docs test holds both halves: the shape of every bundled `<script>`, and the absence of any module-scope listener or `matchMedia` read in the `utils/` modules they import. `ClientRouter` is rendered on every page, and it runs a given script **once per session**: `deselectScripts` stamps `data-astro-exec` on any script it has already seen, so on the second navigation the swapped-in body is never wired. The event fires on the initial load too, so deferring costs nothing. The swap replaces `<body>` and keeps `window`, `document` and the `<html>` element: the initialiser re-runs on every navigation, so what it adds to those three must not stack. The bug is invisible to `tsc`, Biome, the unit suite, `astro check` and the build alike, because every one of them only ever sees the first pageview. `is:inline` scripts are exempt: they are not bundled, and the two that matter, the theme bootstrap and the consent gate in [`Head.astro`](./core/components/head/Head.astro), have to run before paint (ADR 0005, ADR 0013).

The view transition that carries an Article card's image to the page's featured image pairs the two by name, and `featuredImageTransitionName` in [`blurImage/utils/transition.ts`](./core/components/blurImage/utils/transition.ts) is the one spelling of it, which `ArticleCard.astro` and the Article route both call, so the halves cannot disagree.

The Article page's modules lean on markup the route and the renderer produce. `ARTICLE_BODY_CLASS` in [`article/const.ts`](./article/const.ts) names the body the route renders: `ColumnsToggle` and `ReadingProgress` find it by that class and paint nothing without it, and the `article-wrapper--two-columns` the toggle sets (`ARTICLE_COLUMNS_ACTIVE_CLASS`, in the toggle's own `const.ts`) is styled only in `_article.css`. `TableOfContents` highlights the section being read: each entry animates on `--for`, the `scope` the renderer stamps on that heading's `<section>` as `--is`, which `_article.css` turns into a view timeline and lifts to `.article-wrapper` through the `--scopes` list the route writes. The class names travel through those constants, and the docs test holds each one to a stylesheet; the `--for`, `--is` and `--scopes` custom properties have no such constant, and no unit test reads the route, the renderer and `_article.css` together, so a rename of one of them stops the highlight without failing the suite. The renderer also wraps a generic iframe (`iframeEmbed`) in `<div class="iframe-embed">` and leaves a video (`videoEmbed`) bare: `_article.css` keeps every article iframe at `aspect-ratio: 16 / 9`, and makes the wrapper a size container (`container-type: inline-size`) so its frame can say `height: auto`, `min-height: calc(100cqi * 9 / 16)` and `frame-sizing: content-height`, as a block, because the inline iframe a wrapper holds would gain the line's descender gap that a grid item has none of. Today the frame is the same 16:9 box; once the embedded page opts in with `<meta name="responsive-embedded-sizing">`, a browser that implements the property sizes the frame to that page, and the floor is what stops an `auto` iframe falling back to 150px before then. The wrapper is in the two-column `break-inside: avoid` list beside the figures.

An `id` is declared where something reads it: an `aria-*` reference, a `for`, a `url(#…)`, a selector or a script. The zoom icons carried `id="zoom-in"` and `id="zoom-out"` for no reader, names that repeat as soon as a page renders one twice. The docs test rejects a static `id` that nothing else in `src` mentions.

The header loads GSAP when the first click needs it, not when the page does: `buildMenuTimeline` in [`header/utils/interactions.ts`](./core/components/header/utils/interactions.ts) imports it dynamically and `wireMenu` builds the timeline on the first click, so the 70 KB stays out of every page's first load for an animation a reader may never trigger. The state the click changes (`aria-expanded`, the open class, what the menu covers going inert) does not wait for it, and the direction the timeline plays follows that state rather than toggling, so two clicks before it arrives still end where the second one left the menu. A static `gsap` import under `core/` would put the library back on every page, and the docs test rejects one; `contact/` imports it statically because the form island is the only reader of that page.

## Styling

- **Component CSS is not scoped by Astro**: it's a plain global stylesheet imported next to the component, so the class names are the only isolation there is. Not one component uses an Astro `<style>` block, and the docs test keeps it that way: a `<style>` block *would* be scoped, so a single one would make "the class names are the only isolation" quietly false for the next reader.
- **Every class a component writes sits under one block named after it** (`article-card`, `article-card__byline`, and `article-card-wrapper` where the layout needs a wrapper), so a class says which stylesheet declares it. A header atom writes under `header` and a contact form control under `contact-form`. A component may also name the block of a component it renders (the footer places `social-networks__list`), a mix from `@styles/global`, the block an inline SVG carries (`stretch-arrow__tip`), the `page` hooks on `<html>` and the vendor's own class (`calendly-inline-widget`). Every rule of a component stylesheet opens with a class, never an element type. The docs test holds both.
- **A class or an id that a script or a spec reaches for is spelled once, in the component's `const.ts`**, which the template, the script and the specs import (`HEADER_MENU_BUTTON_CLASS`, `TAB_CLASS`, `EMAIL_BUTTON_CLASS`). The stylesheet spells it again, because CSS imports nothing, and the docs test holds the rest: every `*_CLASS` constant is selected by a stylesheet, no template respells one, and no script, spec or built-output test writes a class selector of its own beyond the mixes of `global.css` and `modifiers.css`. So a rename is one edit in `const.ts` and one in the stylesheet, and a spec that locates by a renamed class stops compiling instead of skipping a case.
- **Cross-block behaviour is a block, mixed in**, applied alongside the component's own block, a BEM *mix*: `class="header__menu__link underline-on-hover clickable"`. The mixes live in two files under `@styles/global`, split by cascade layer: behavioural mixes in [`modifiers.css`](../styles/global/modifiers.css) (`@layer modifiers`), typographic and layout ones in [`global.css`](../styles/global/global.css) (`@layer global`). Component stylesheets are unlayered, so they beat both without extra specificity, and a block may override a mix for itself: [`menu.css`](./core/components/header/atoms/menu/menu.css) paints `.header__menu__link.current-page` gold rather than the `--primary-main` the mix gives it. The behavioural mixes:
	- `underline-on-hover`: a link or link-like button that underlines on hover
	- `clickable`: anything that responds to a press
	- `inverted-color-scheme`: a section that inverts against the page, and the header's cue to invert its logo and menu button over it
	- `current-page`: the entry pointing at the route already being viewed
	- `item-wrapper`: a list item whose card link stretches over the whole item
	- `visually-hidden`: an element the design hides but a screen reader and the tab order must still reach, such as the theme toggle's checkbox; `display: none` takes a control out of both
- Component CSS queries the container [`styles/base/base.css`](../styles/base/base.css) names for its page (`@container home-page (width <= 960px)`); the styles guide says which routes get one.

## Islands

The React components: `about/worldGlobe` (three / react-globe.gl), `contact/contactForm` (react-hook-form) + `contactFormProvider` (reCAPTCHA), `contact/form/*`, `contact/spinner`. Everything else is `.astro`, rendered on the server. `astro.config.ts` compiles them with the React Compiler (`react({ compiler: true })`), which memoises every component and hook itself.

Writing a React component does not create an island. There are only two hydration roots in the whole site: `WorldGlobe` in [`LittleMoreOfMe.astro`](./about/components/littleMoreOfMe/LittleMoreOfMe.astro), `ContactFormProvider` in [`Tabs.astro`](./contact/components/tabs/Tabs.astro). Every one is `client:load`, so the server renders it and the browser hydrates it on load, and a page that renders neither root ships no React: the built-output test holds that no prerendered page but About carries an `<astro-island>`. `WorldGlobe` is `client:load` even though its inner component reads `window.innerWidth` in a `useState` initialiser: the root wraps it in `<Suspense>` and the inner component opens with `use(browser())` from `react-dom`, so the server emits the fallback, an `<aside>` of the canvas's height, and the browser renders the rest on hydration without a recoverable error. That is what puts the reserved height in the HTML instead of leaving the island empty until its script runs. `ContactFormProvider` is also `client:load`, so the form is server-rendered and hydrated on load, which it can afford because `react-google-recaptcha-v3`'s provider renders its children either way and `useGoogleReCaptcha` simply has no `executeRecaptcha` until the script is in: the same absence the `getRecaptchaToken` prop already models below. The other React files are children of those and hydrate with their root.

The cookie banner is not an island: `vanilla-cookieconsent` is framework-free, and a root for one button would put React on every page. [`CookieConsent.astro`](./core/components/cookieConsent/CookieConsent.astro) renders the Manage cookies button on the server, and its bundled script runs `initCookieConsent` from [`utils/interactions.ts`](./core/components/cookieConsent/utils/interactions.ts) on `astro:page-load`. That function resets the library before it runs it, because `run` does nothing while the library believes it is running and a swap takes the banner it built with the old body: without the reset the second page of a visit has no banner and a button that opens nothing. It binds the button on the page it initialises, so a swapped-in footer is wired. The unit tests hold a second page's banner and preferences, and the Client Router spec holds them in a browser. The consent default the banner depends on stays an inline script in [`Head.astro`](./core/components/head/Head.astro) (ADR 0013).

A hydration directive serializes an island's props into the page's HTML. `toCityPoints` in [`about/utils/globe.ts`](./about/utils/globe.ts) maps cities down to the `CityPoint` the globe needs (coordinates, name, the City's Slug): `lat`/`lng` are `react-globe.gl`'s default accessor names and `label` is what the pin prints, not the domain's names, and [`Cities.astro`](./about/components/cities/Cities.astro), the second consumer, needs the fields the globe drops. The Slug travels rather than being re-derived in the browser: it is what `Cities.astro` puts on the card's `id`, and what a pin scrolls to. The globe paints from tokens, not from colours of its own: [`worldGlobe/utils/palette.ts`](./about/components/worldGlobe/utils/palette.ts) resolves the tokens `WORLD_GLOBE_CONFIG` names (`--gold-bright` for the land, `--surface` for the sea) to the hex the browser paints, by reading the colour an element takes from the token back off a canvas, which handles `light-dark()`, `color-mix()` and oklch alike where `react-globe.gl` parses hex, rgb and hsl only, and it reads them again whenever `data-theme` changes on `<html>`, so the toggle repaints the globe. The countries file the globe fetches is checked rather than trusted: [`worldGlobe/utils/countries.ts`](./about/components/worldGlobe/utils/countries.ts) checks [`public/countries.json`](../../../public/countries.json) against a zod schema (a `features` list of GeoJSON `Feature`s with `Polygon` or `MultiPolygon` geometry) and answers an empty list for anything else, so an unreadable or reshaped file draws an empty globe. `ContactForm`'s `submit` and `getRecaptchaToken` are functions, which cannot survive that trip, so `ContactFormProvider` binds them in the browser and passes them down, and the hydration root itself takes none.

## Data

Components read content through `getCollection`/`getEntry` from `astro:content`, never by calling Contentful or `@infrastructure` directly: the docs test fails on either import anywhere under [`src/ui`](..). Dereferencing a stored `reference()` is `resolveArticle` / `resolveArticles` in [`core/utils/entries.ts`](./core/utils/entries.ts) and only that: one reference or a list of them, and `getEntry` is called nowhere else under `src/ui` or `src/pages`. The pair drops what no longer exists rather than answering a hole, keeps the order the collection stored, and answers a plain promise, so no caller writes its own `getEntry` fan-out, re-sorts what comes back, grafts a resolved entry onto the entity that referenced it, or reaches for Effect to await one entry; nothing under `src/ui` imports `effect` at all, which is the promise ADR 0004 makes about the read path. [`RelatedArticles.astro`](./core/components/relatedArticles/RelatedArticles.astro) and the tag route resolve a list: the tag route shows the order `sortFavoriteFirst` decided upstream, and `RelatedArticles` shuffles the list it resolved once at build time, with `shuffle` in [`relatedArticles/utils/shuffle.ts`](./core/components/relatedArticles/utils/shuffle.ts), and hands that one order to the slides and to the `ItemList` that describes them; [`about.astro`](../../pages/about.astro) resolves the single Latest Article the Author carries. Server mutations go through the generated `astro:actions` client, never by importing `src/actions`, and `actions.contact` is the only mutation in the tree. It is bound in [`ContactFormProvider.tsx`](./contact/components/contactFormProvider/ContactFormProvider.tsx) (which reaches `astro:actions` and reCAPTCHA) and handed to [`ContactForm.tsx`](./contact/components/contactForm/ContactForm.tsx) as the `submit` and `getRecaptchaToken` props, so the form imports nothing from `astro:*` and its status machine is asserted in the dom project (ADR 0016). What `submit` answers is a `ContactSubmission` from [`contact/utils/submission.ts`](./contact/utils/submission.ts), not the action's own result: the form reads the 401 that locks it out, and an answer that is neither ok nor an error is undelivered rather than silent. `getRecaptchaToken` is **absent, not failing, while reCAPTCHA is still loading**: the provider hands the prop down only once `executeRecaptcha` exists, and a submit made before then does nothing: it neither sends nor accuses. Collapsing the two into one function that answers `undefined` is what turns "the script has not loaded yet" into "you are a bot": a legitimate visitor who submits quickly gets accused.

`articleHref` and `tagHref` in [`@const/routes.ts`](../../const/routes.ts) turn a Slug into a path, `projectHref` turns a Project's `id` into an anchor on `/projects`, and the JSON-LD builders in [`core/utils/jsonLd.ts`](./core/utils/jsonLd.ts) take Slugs, ids or paths and call `absoluteUrl` themselves. The Featured Article's share intents are `buildArticleShareLinks` under that component's `utils/`. What a tag route calls itself is owned by `tagPageCopy` in [`core/utils/tagPage.ts`](./core/utils/tagPage.ts): it reads the stored `type` and names an Author rather than hashing their slug, which is the only thing in the tree that reads that discriminant after the tag index sets it.

Bianca's email address is owned by [`core/components/emailButton`](./core/components/emailButton). [`EmailButton.astro`](./core/components/emailButton/EmailButton.astro) takes a `label`, or `shows="address"`, and never the address itself: the server renders the placeholder `our email address`, and `activateEmailButtons` in that component's [`utils/interactions.ts`](./core/components/emailButton/utils/interactions.ts) decodes `CONTACT_DETAILS.ENCODED_EMAIL_BIANCA` in the browser: to fill the text in, and to open the composer on a click. So the address is never server-rendered, which is the whole point of the base64. The class the listener matches, `EMAIL_BUTTON_CLASS`, and the `data-shows="address"` that marks a button as the address live in [`const.ts`](./core/components/emailButton/const.ts). The listener answers a trusted click only, so a script cannot dispatch its way to the address.

The Contact page's `?tab=` deep link is owned by [`tabs/utils/tabs.ts`](./contact/components/tabs/utils/tabs.ts). The query key is declared beside the tab ids, in [`tabs/const.ts`](./contact/components/tabs/const.ts): `activeTab` reads it for the server render, which sees the query string only because `contact.astro` renders on demand, `initTabs` reads it off the page's own URL, and the `astro:page-load` script in `Tabs.astro` hands it nothing, so the halves that read the deep link and the half that writes it cannot spell the key differently. That module also keeps the two directions apart: restoring the tab a URL asks for only applies it and touches no history at all, while a reader's click publishes it as a `replaceState` (a view change on the same page, not a navigation), carrying the router's own `history.state` rather than a fresh one. A restore that pushed an entry would trap the reader: Back would return to the un-suffixed URL, `ClientRouter` would re-run `astro:page-load`, and the tab would be pushed again. [`e2e/contact-tabs.spec.ts`](../../../e2e/contact-tabs.spec.ts) imports `TAB_CLASS` and `TabId` from that `const.ts`, so a renamed class stops it compiling instead of switching it off, and one helper skips it when the page serves no tabs at all (`HIDE_CHROME` serves `/contact` as the placeholder). The requested tab id, a clicked tab's `data-target` and the `Calendly` global are checked against zod schemas in that module: an unknown tab id falls back to the first tab or is ignored, and a `Calendly` global that is not the vendor's object makes the module load the vendor script rather than call it.

The Appointment tab's Calendly frame follows the height of the booking page. `Tabs.astro` puts `data-resize="true"` on the `.calendly-inline-widget` div, the booking page then posts `calendly.page_height` to the parent, and the vendor's `widget.js` sets that height on the container, so the page does not scroll inside its frame; `tabs.css` keeps `height: 700px` as the height before the first message arrives, as the vendor's own embed does. The policy needs nothing for it: a `postMessage` is outside the CSP, and `frame-src` already names the booking origin. The injected frame carries `height="100%"`, which the stylesheet overrides with `height: auto`, `min-height: 100%` and `frame-sizing: content-height`: today the frame is the height of its container, so nothing moves, and once the booking page opts in with `<meta name="responsive-embedded-sizing">` a browser that implements the property sizes the frame to that page. The floor is what keeps it from falling back to the 150px an `auto` iframe has by default. [`calendly.test.ts`](../../const/calendly.test.ts) holds the attribute, the starting height and the three declarations.

**zod reaches the browser only where it is already paid for.** `astro/zod` bundles to a shared chunk of about 25 KB gzipped, which `/contact` loads anyway for `ContactForm`'s resolver and the lazily loaded globe canvas takes on top of `three`. A browser module anywhere else checks what it reads by literal comparison instead: the stored theme preference (`readPreference`) and the Green Web Foundation answer (`isGreenHost`, which believes only `green === true`) on every page, and the stored columns flag (`isColumnsEnabled`) on every Article, would each pay that chunk for one yes or no, and the `is:inline` scripts in `Head.astro` cannot import at all. [`CarbonBadge.astro`](./core/components/carbonBadge/CarbonBadge.astro) runs `renderCarbonBadge` from its [`utils/carbon.ts`](./core/components/carbonBadge/utils/carbon.ts), and its template reads the badge's id, `BADGE_ID`, from the same module.

What "the reader's theme" means is owned by [`core/components/themeToggle`](./core/components/themeToggle), and it is two things rather than one. [`const.ts`](./core/components/themeToggle/const.ts) declares the storage key, the `data-theme` attribute and the vocabulary: a **preference** (`dark`, `light` or `system`) and the theme actually painted, which [`utils/preference.ts`](./core/components/themeToggle/utils/preference.ts) resolves from that preference and `prefers-color-scheme`. Nothing stored, or anything unrecognised, reads as `system`. Only a click on the toggle persists: [`utils/theme.ts`](./core/components/themeToggle/utils/theme.ts) paints without writing, and its `prefers-color-scheme` listener applies a change only while the preference is `system`. So mirroring the operating system stores nothing, and an operating-system switch under a reader who chose a theme repaints nothing. The render-blocking bootstrap is the same rule, and the same module builds it: `Head.astro` renders `THEME_BOOTSTRAP_SCRIPT` with `set:html` on the `is:inline` tag ADR 0005 requires, so the key, the attribute and the fallback are never restated as literals in a template that neither Biome nor `tsc` reads. `theme.ts` also paints the incoming document on `astro:before-swap`, because the swap replaces the attributes of `<html>` with the incoming document's, which carries no `data-theme`.

Which routes a search engine is told to leave alone is `NOINDEX_ROUTES` in [`@const/noindexRoutes.ts`](../../const/noindexRoutes.ts), declared once: `isNoindexRoute` answers the sitemap filter in `astro.config.ts` and [`Seo.astro`](./core/components/seo/Seo.astro), `PAGES_ROUTES` takes the two legal paths from it, and `public/robots.txt` repeats them because a static file imports nothing, which the docs test holds equal. A page on one of those routes passes no `robots` of its own; `404` and `500` are outside the sitemap and pass theirs. The default share image is a 1200 by 630 card, [`bianca-fiore-card.jpg`](../assets/images/jpg/bianca-fiore-card.jpg): the portrait the About, Home and Contact pages render, cropped from the top of the face to its landscape band (a 994 by 522 window taken 130 pixels down), scaled to 1200 by 630 and saved at quality 78. A card is about a tenth of the original's weight, and the docs test holds the size, the dimensions and that `seo/const.ts` imports the card and not the portrait.

Whether a page shows its chrome at all is `siteChrome` in [`core/utils/siteChrome.ts`](./core/utils/siteChrome.ts): the only reader of `HIDE_CHROME` in the tree, answering `showsHeader`, `showsBreadcrumbs`, `showsTableOfContents` and `servesRealContent` for a URL. [`BaseLayout.astro`](./core/components/baseLayout/BaseLayout.astro) asks it whether to render the `Header` and whether to serve the `<slot />` or [`UnderConstruction`](./core/components/underConstruction/UnderConstruction.astro), the placeholder, the Article route asks it about the Table of Contents, and [`Breadcrumbs.astro`](./core/components/breadcrumbs/Breadcrumbs.astro) asks it about itself, which is why every call site renders it unconditionally and none of them can hide it on one route and forget on the next. Deny by default: a route is served for real only if it is under one of the published routes `siteChrome` names, so a new page inherits the placeholder rather than the exemption.
